# WarpFactor — архитектура

2D-игра про автоматизированное производство, выживание и оборону мобильной базы. Godot 4.7.2,
GDScript со статической типизацией, только 2D.

> С 2026-09-14 цели игры изменены: см. `docs/GDD.md` (дизайн) и `docs/ROADMAP.md` (новый план этапов).
> Этапы 1–4 ниже описывают фабричное ядро, которое переносится без изменений. Решения, помеченные ⚠,
> пересматриваются по новому плану.

## Принятые решения

| Тема | Решение |
|---|---|
| Движок | Godot 4.7.2 (Steam), рендер GL Compatibility |
| Мир ⚠ | Уровни создаются заранее вручную (файлы `.fwmap`), генерации и сидов в игре нет. Карта конечная, чанки 32×32 — для отрисовки и пространственного поиска |
| Редактор уровней ⚠ | Внутриигровой, после всех этапов. До него тестовые карты собирает `tools/build_test_levels.gd` |
| Прогрессия ⚠ | Своя на каждом уровне: стартовые здания, пороги разблокировок, контракты. Цели уровня открывают следующий |
| Творческий режим | Галочка при запуске уровня: постройки не расходуются, радиус дрона не ограничен |
| Игрок | Дрон: WASD, камера следует за ним, действия в радиусе 10 тайлов, медленная добыча руды |
| Хранение | Ядра нет. Предметы лежат в складах и инвентаре дрона: ячейки со стаками, как в Factorio |
| Стоимость | Постройка — предмет: крафтится руками (очередь со временем), ставится из инвентаря, при сносе возвращается |
| Снос с содержимым | Содержимое уходит в инвентарь дрона; что не поместилось — теряется (с уведомлением) |
| Топливо | Уголь — топливо печи, термогенератора и бойлера. Буры, сборщик и научный цех — от электричества; турели, логистика и насос — без него |
| Контент | Ранняя игра по заметкам пользователя: гематит, камень, уголь, малахит, вода; таблицы — `docs/CONTENT.md` |
| Конвейеры | Модель «слот + прогресс» на тайл (как в Mindustry), хранение SoA, сон/пробуждение |
| Графика | Процедурные плейсхолдеры; спрайты из Aseprite подменяются через поля `sprite`/`texture`/`icon` в `.tres` |
| UI | Собирается кодом, тема Gruvbox (`ui/ui_theme.gd`), RU/EN через `i18n/strings.csv` |

## Слои

**Данные** (`Resource` в `.tres`): `ItemType`, `FloorDef`, `OreDef`, `BuildingDef`, `LevelDef`, `DroneDef`.
`Registry` загружает их из фиксированных папок, сортирует и назначает плотные int-индексы.
В симуляции предметы, полы и руды — только индексы.

**Модель** (без нод):
- `GameWorld` — сетка, здания, симуляция, дрон; все действия игрока (стройка, снос, поворот, перенос предметов)
  с проверкой радиуса дрона и наличия постройки в инвентаре.
- `WorldGrid` — плоские `PackedByteArray`/`PackedInt32Array`: пол, руда, id здания на тайл.
- `BuildingManager` — проверка размещения (`OK/REPLACE/SAME/OUT_OF_BOUNDS/BAD_TERRAIN/OCCUPIED/NO_ORE`,
  `NO_ITEM`/`OUT_OF_RANGE` добавляет `GameWorld`), установка, поворот, снос, поиск по тайлу и рамке через списки
  зданий по чанкам. Сигналы `building_added/removed/rotated`.
- `Building` — `RefCounted`, не нода. Хуки: `on_placed`, `on_removed`, `on_rotated`, `on_proximity_changed`,
  `update_tick`, `accept_item/handle_item`, `collect_contents`, `get_info_lines`, `get_config/set_config`.
  Любое здание можно повернуть; спрайты рисуются «вправо».

**Представление** (ноды, подписаны на сигналы модели):
- `TerrainView` — два `TileMapLayer`, чанки заполняются лениво с бюджетом времени на кадр;
  под ними обзорная текстура (1 тексель = 1 тайл), при масштабе < 0.3 заменяет тайлмапы (LOD).
- `BuildingLayer` — одна нода `BuildingChunkView` на чанк, перерисовка только грязных чанков.
  Все спрайты зданий лежат в одном атласе, поэтому здания батчатся.
- `GridOverlay` — сетка одним прямоугольником с шейдером; `OreOverlay` — карта ресурсов одной текстурой.
- `PlacementPreview` — призраки, рамка сноса, подсветка.

**Ввод**: `CameraController` (следует за дроном, СКМ временно смещает взгляд, зум к курсору, компенсация
масштаба UI), `DroneController` (WASD → направление полёта),
`ToolController`: строительство и протягивание (ЛКМ), выделение области (ПКМ с зажатием) со сносом (X)
и копированием в план (C → вставка ЛКМ, поворот R), пипетка, настройка зданий, добыча руды (ЛКМ по руде). Позиция курсора берётся
из событий ввода, а не из системного курсора. Схема управления версионирована (`InputActions.BINDINGS_VERSION`):
сохранённые привязки старой схемы сбрасываются.

**Интерфейс**: `Hud`, `BuildMenu` (только вкладки и кнопки, описание в подсказке), `InventoryWindow` (инвентарь + крафт или содержимое здания), `CraftQueuePanel`,
`ItemSlot`, `PauseMenu`, `MainMenu`, `LevelSelect`, `SettingsMenu`.
Controls под `CanvasLayer` не наследуют тему окна — корням таких интерфейсов тема назначается явно.

**Автозагрузки**: `Events` (уведомления UI), `Settings` (настройки и привязки клавиш), `Session` (переходы сцен).

## Настройки

Описываются списком `SettingEntry` (BOOL / CHOICE / RANGE). По этому списку строится меню,
выполняются сохранение в `user://settings.cfg` и применение. Привязки клавиш — по физическим кодам
(не зависят от раскладки), формат `key:Ctrl+S` / `mouse:1`.

## Формат карты `.fwmap` (версия 1)

ZSTD-сжатие; magic `FWMP`, u16 версия, размер, таблицы строковых id полов/руд/зданий,
слои пола и руды (w×h байт), список предустановленных зданий. Индексы в файле переназначаются
по id, поэтому новые типы в `.tres` не ломают старые карты.

## Симуляция (этап 2)

**Такт.** `SimClock` накапливает время кадра и выполняет фиксированные тики `Simulation.step()`
(30 в секунду; ×2/×4 — больше тиков той же длины, не больше 8 за кадр). `alpha` — доля до следующего
тика, используется только отрисовкой. Меню паузы блокирует часы.

**Тик.** Планировщик (`Scheduler`, timing wheel) будит здания, чьё время пришло → `ConveyorSystem`
двигает бодрствующие ленты → бодрствующие здания выполняют `update_tick` → статистика.
Разбуженное во время тика здание обновится на следующем — предмет не пройдёт две постройки за тик.

**Сон и пробуждение.** Пустые и заблокированные ленты, бур между предметами, источник без места
не обновляются. Будят их: пришедший предмет, `notify_space` получателя (подписка `add_waiter`),
изменение соседства, планировщик.

**Ленты** (`ConveyorSystem`, SoA): до 3 предметов на тайл, прогресс в целых единицах
(1200 на тайл, зазор 480) — без накопления ошибок float, детерминированно. Передача вперёд
сохраняет перебег, вставка сбоку — на середину тайла. Встречные ленты не передают друг другу.
Ссылки между лентами — по id зданий (индексы меняются при удалении).

**Передача предметов**: `accept_item` / `handle_item`, `dump` — по кругу соседям (`proximity`).

**Экономика.** `GameWorld.build/demolish/rotate_building`: стоимость списывается из `CoreStorage`,
при сносе возвращается; содержимое снесённого здания уходит в ядро как доставка. Ядро сжигает
излишек сверх лимита, но засчитывает его. `ItemStats` — скользящее окно +/− в секунду.

**Отрисовка предметов**: один `MultiMeshInstance2D`, иконки в атласе-полосе (шейдер выбирает ячейку
по `INSTANCE_CUSTOM`), позиция интерполируется между тиками, только видимые чанки, LOD при масштабе < 0.4.

## Логистика (этап 3)

| Здание | Класс | Поведение |
|---|---|---|
| Перекрёсток | `Junction` | Очередь на каждое направление (6 предметов), выход на противоположную сторону не раньше 8 тиков |
| Маршрутизатор | `Router` | Как в Mindustry: буфер на 1 предмет, отдаёт по кругу во все стороны, в том числе назад источнику (кроме мгновенных зданий). Приоритетные вход и выход — настройка (этап Д) |
| Сортировщик | `Sorter` | Мгновенно: выбранный предмет вперёд, остальные в стороны; инверсия (настройка) — наоборот |
| Мостовой конвейер | `BridgeConveyor` | Связь со следующим мостом до 4 тайлов по прямой, буфер 10; конец цепочки отдаёт соседям, но не назад |
| Разгрузчик | `Unloader` | Как в Mindustry: балансирует предмет между соседями по заполненности (`get_load_factor`). Берёт из складов, заводов (сырьё и продукция) и буров, отдаёт лентам и зданиям, но не складам |

- **Уровни и пропускная способность.** `LogisticDef.throughput_of` ссылается на ленту своего уровня:
  здание пропускает не чаще раза в `get_ticks_per_item()` тиков, как эта лента при плотном потоке
  (обычная — 6 предм./с). Титановые версии были до этапа Д и вернутся позже; механика уровней осталась.
  Делитель держит предмет на интервал − 1 тик, перекрёсток и мост выдерживают интервал на выходе,
  разгрузчик — между перекладываниями.
- **Мгновенные здания** (`PassThroughBuilding`) не имеют буфера: предмет проходит сквозь них
  внутри `accept_item/handle_item`; «вперёд» — сторона, противоположная источнику. Цепочки ограничены
  глубиной 8. После предмета здание не принимает следующий интервал и просыпается за тик до его конца,
  чтобы разбудить ожидающих (ленты обновляются в тике раньше зданий). Заблокированная лента ждёт
  и само здание, и его соседей.
- **Настройка** (`get_config_kind/get_config/set_config`): фильтр-предмет, инверсия (`supports_inversion`,
  у сортировщика настройка — словарь `{item, inverted}`), приоритеты маршрутизатора `{in, out}`,
  рецепт сборщика (id) или смещение до связанного моста.
  Меняется через `GameWorld.configure` (встречная связь мостов снимается), копируется пипеткой,
  применяется при строительстве. Клик пустой рукой выбирает настраиваемое здание; для моста клик по другому
  мосту в дальности связывает их. Протягивание мостов ставит их с шагом дальности и связывает цепочкой.
- **Оверлей загрузки лент** (L): пустые, поток, плотный поток, затор.

## Производство (этап 4)

**Рецепты — данные** (`items/recipes/*.tres`): `Recipe` = список `Consume` + список `Produce` + время цикла.

| Класс | Назначение |
|---|---|
| `Consume` (абстрактный) | `accepts_item`, `item_capacity`, `is_satisfied`, `consume`, `refund`, `efficiency`, `describe_missing` |
| `ConsumeItems` | Предметы из входного буфера |
| `Produce` (абстрактный) | `can_output`, `produce`, `output_items`, `display_stacks/chances` |
| `ProduceItems` | Гарантированный выход |
| `ProduceWeighted` | Случайный выход по весам через RNG мира (детерминирован от id уровня) |

`Crafter` работает только через этот интерфейс: принимает входы рецепта в буфер, в начале цикла списывает их,
спит до конца цикла (`finish_tick`), кладёт результат в выходной буфер и раздаёт соседям по одному предмету
за тик. Статусы: работает / нет сырья (с перечнем) / выход забит. Время цикла делится на минимальную
`efficiency` входов — так в будущем `ConsumePower` замедлит завод при нехватке энергии без правок `Crafter`.

Заводы этапа 4 (дробилка, пресс, сепаратор и др.) удалены на этапе Д; сейчас заводов два — печь и сборщик
с несколькими рецептами, см. раздел этапа Д и `docs/CONTENT.md`. Цикл завода с этапа Д — прогресс
с учётом питания, а не `finish_tick`.

**Подсказка у курсора** (`BuildingTooltip`): название, рецепт иконками с шансами и временем, статус цветом,
прогресс цикла, буферы. Характеристики заводов показываются и в меню строительства.

## Дрон, инвентарь и крафт (этап 5)

**Предметы-постройки.** У каждой строящейся постройки есть `ItemType` с полем `building`
(`items/types/buildings/`). Здание хранит индекс своего предмета (`item_index`), а не ссылку —
иначе ресурсы образовали бы цикл и не освобождались. Постройки ездят по лентам и лежат в складах
как обычные предметы.

**`Inventory`** — ячейки (предмет + количество до `stack_size`). Суммы и число ячеек по каждому
предмету кэшируются, поэтому `space_for` — O(1): склад, который лента проверяет каждый тик, не
сканирует ячейки. У дрона инвентарь автосортируемый. `Inventory.Budget` — копия количеств для
планирования ряда построек.

**`StorageBuilding`** (контейнер 16 ячеек) принимает предметы, пока есть место. Когда место
освобождается (разгрузчик или игрок забрали предмет), будит ленты через `notify_space`.

**`Drone`** — модель в тике симуляции (после зданий): движение с интерполяцией отрисовки, радиус действий
`can_reach_*`, добыча руды (`mine_ticks = база + твёрдость × коэффициент`, уровень руды ≤ `mine_tier`),
очередь крафта.

**`CraftQueue`** — очередь единиц. Единица — полный план одного крафта: недостающие промежуточные детали
(например, шестерня для ленты) докрафчиваются в той же единице. Сырьё списывается при постановке
и полностью возвращается при отмене. Результат выдаётся по окончании; при полном инвентаре очередь ждёт.
Рецепты (`HandRecipe`) строит реестр из `BuildingDef.cost`, `craft_time`, `craft_amount`.

**Действия игрока** (`GameWorld`): `check_build`/`build` (радиус, предмет в инвентаре; при замене сначала
снос старого с возвратом), `demolish` (радиус, место под постройку; `last_error`, `last_lost_items`),
`rotate_building`, `player_take`/`player_put` (окно здания). Интерфейс здания для окна:
`has_player_window`, `get_inventory`, `accepts_player_items`, `get_player_stacks`, `take_player_items`.

## База и планета (этап 6)

**`Run`** (забег) владеет двумя `GameWorld` — планетой (карта уровня) и базой (`BaseDef`: пустое
пространство 24×24 из металлических плит), общим дроном и `GatewayLink`. `SimClock` вызывает `Run.step()`:
обе симуляции тикают всегда, какой бы мир ни был на экране. Дрон обновляется в симуляции того мира,
где находится (`drone.world`); действовать (строить, сносить, настраивать, брать предметы) можно только
там (`GameWorld.has_drone`).

**Центральный шлюз и пара** (`GatewayBuilding`, `GatewayDef`): шлюз 3×3 ставится на планете на место
посадки, пара — в центр базы. Портов два, стороны зеркальные: предмет, вошедший в западный порт шлюза,
выходит из западного порта пары; вошедший в восточный порт пары — выходит из восточного порта шлюза.
Между мирами — две очереди `GatewayLink` (по 10 предметов); выдача ограничена пропускной способностью
обычной ленты. Порт принимает предмет только от здания, стоящего на тайле порта. Когда очередь
освобождается, шлюз будит ленты у входа на другой стороне (`notify_space` в чужом мире).

**Переход дрона**: над шлюзом (или парой) HUD показывает «F — войти в базу / выйти на планету»;
`Run.use_gateway` переносит дрона в ту же точку другой стороны и шлёт `drone_changed_world`.

**Площадка**: `GameWorld.pad_rect` — 15×15 вокруг шлюза, рисуется пунктиром (`PadOverlay`), в инфо-панели
помечена. Шлюз и пара поворачиваются независимо (R), стороны портов поворачиваются вместе со зданием.

**Представление** (`WorldView`): у каждого мира свои террейн, сетка, граница, здания, предметы, оверлеи,
площадка. Неактивный вид скрыт и заморожен (`PROCESS_MODE_DISABLED`), изменения зданий копятся грязными
чанками. При переходе `Game` меняет активный вид и переключает на новый мир инструменты (`ToolController.set_world`),
камеру (границы карты) и панели HUD. Свойства `Game.terrain/building_layer/...` отдают активный вид.

## Телепорт и забег (этап 7)

**Звёздная карта** (`StarMap`): граф планет по шагам — старт, затем 2–3 планеты в шаге, связи только вперёд.
Детерминирована от сида забега, достраивается на `RunDef.visible_depth` шагов вперёд. Узел хранит тип
(`PlanetTypeDef`: обычная или пустошь), сид, размер, список руд и код для названия.

**Генерация** (`PlanetGenerator`): пол — шум с пятнами, скалы — второй шум и кромка по краю, руды — кляксы
(первая залежь каждой руды недалеко от посадки). В центре — место посадки: расчищенная земля и
металлическая платформа площадки без руды. У пустоши руд нет и `safe = true`.

**Телепорт** (`Run`): `start_teleport(node)` → зарядка `RunDef.charge_seconds` в тиках забега → `_teleport`:
- постройки целиком на площадке сохраняются (`def`, смещение, поворот, `get_config`, `save_state`);
- генерируется новая планета, её тик выставляется равным тику базы;
- шлюз ставится в центр с прежним поворотом, постройки — на те же места площадки
  (`set_config` + `load_state`);
- `GatewayLink` переключается на новый шлюз, очереди сохраняются;
- дрон на планете переносится на новую площадку;
- старый мир освобождается, строится `TeleportSummary`, шлётся `planet_changed`.

`Game` заменяет `WorldView` планеты и переключает панели, HUD показывает окно итога.

**Состояние зданий** (`save_state`/`load_state`) — буферы, прогресс и абсолютные тики (миры забега
синхронны). Ленты отдают предметы через `ConveyorSystem.export_items/import_items`. На этом же будут
построены сохранения (этап 8).

**Интерфейс**:
- `TeleportWindow` (клик по шлюзу): очереди, `StarMapView`, описание планеты, телепорт и отмена;
- `SummaryWindow`: итог прибытия;
- в HUD — отсчёт зарядки и отметка «безопасно»;
- в меню — `NewRunScreen`: сид, превью первой планеты, творческий режим.

## Сохранения (этап 8)

**Файл** `user://saves/<слот>.fwsave`:
- `FWSV`, версия;
- заголовок: название, планета, в базе ли дрон, дата, время игры — читается без распаковки тела;
- тело: ZSTD от `var_to_bytes` словаря секций.

Автопрогон пишет в `user://saves_autoshot/`.

**Секции**:
- `tables` — id предметов, полов, руд;
- `run` — сид, уровень, звёздная карта, зарядка телепорта;
- `link`, `drone` — инвентарь с подсказками ячеек и очередь крафта;
- `planet`, `base`.

**Мир в сохранении**:
- размер, слои пола и руды, площадка, состояние RNG;
- здания с их id, типом, поворотом, настройкой, `save_state`, курсором раздачи;
- выдача id (ёмкость, свободные);
- внутренности симуляции (`Simulation.save_runtime`): тик, порядок бодрствующих зданий, корзины планировщика,
  ожидающие, а у лент — порядок в SoA, бодрствующие, флаги ожидания и свежести.

При загрузке ленты ставятся первыми в сохранённом порядке — их индексы совпадают. Затем остальные здания
по id (`BuildingManager.place(..., forced_id)`), затем восстанавливается симуляция.

**Точное продолжение**: сохранение → загрузка → сохранение даёт те же байты, а прогон после загрузки
совпадает с непрерывным. Это проверяет тест на фабрике со всеми видами зданий, шлюзом, электросетью и трубами.

**Перенос индексов**: `SaveContext.begin(таблица id предметов)`. Если порядок предметов изменился,
загрузчики состояний прогоняют индексы через `SaveContext.item/items/counts`; исчезнувшие предметы
выбрасываются, пропавшие типы зданий пропускаются с предупреждением. Пол и руда переносятся по своим таблицам.

**Когда сохраняется**:
- автосохранение по времени игры (настройка 2/5/10 мин), перед телепортом (`Run.teleport_starting`)
  и после прибытия;
- F5 / F9 — быстрые;
- слоты — в меню паузы (`SavesScreen`);
- главное меню: «Продолжить» (последнее) и «Загрузить».

Загрузка перезапускает игровую сцену через `Session.load_game`.

## Угроза и враги (этап 9)

**Данные**:
- `EnemyDef` (`enemies/defs/`) — прочность, скорость, радиус, урон, пауза и дальность атаки, стоимость в очках угрозы.
  Три типа: ползун (быстрый, ближний бой), стрелок (атака на 3.5 тайла), громила (медленный, ломает постройки).
- `ThreatDef` (`enemies/threats/`), ссылка из `PlanetTypeDef.threat`:
  - тихое начало, затишье после первой волны и его множитель;
  - порог, ниже которого волны идут встык;
  - время появления врагов волны;
  - бюджет: за волну и за минуту на планете (от глубины звёздной карты не зависит);
  - враги с номером волны, с которой приходят, и весом; число точек появления; предел живых.
- `BuildingDef.health` и `solid`. Ленты и логистика проходимы (враги идут поверх, но бьют их),
  остальное твёрдое. `get_path_cost()` = 8 + прочность/25.
- `DroneDef`: прочность, пауза появления, неуязвимость после появления, радиус подбора груза.

**Модель** (всё в тике мира, порядок — `Simulation.step`):
1. здания;
2. `ThreatDirector.update` — начало волны по расписанию, выпуск врагов из очереди;
3. `FlowField.update` — порция пересчёта поля;
4. `EnemySystem.update` — движение, выбор цели, атака, раздвигание толпы;
5. дрон.

**Поле потоков** (`FlowField`):
- Дейкстра с корзинами от тайлов центрального шлюза.
- Цена тайла: скала непроходима, земля 1 (у скал 2), проходимые постройки как земля,
  твёрдые — «с ценой» по прочности.
- Считается порциями по 3000 узлов за тик во втором буфере; готовое поле подменяет старое, растёт `version`.
- Постройка или снос твёрдого здания помечают поле грязным. Начатый пересчёт доходит до конца и запускается снова.
- Маска `blocked` (открыто / скала / твёрдое) — для столкновений врагов.

**Враги** (`EnemySystem`):
- Плоские массивы: uid, тип, позиция и прошлая позиция, направление, прочность, тик атаки, цель, преграда,
  следующий тайл и версия поля.
- Следующий тайл — сосед с наименьшей ценой (по диагонали — без срезания углов).
- Упёрся передним краем в твёрдую постройку на пути — встаёт и бьёт её; скала — скользит вдоль.
- Цель раз в 10 тиков: преграда, затем дрон в радиусе, затем ближайшая постройка.
  Атака мгновенная; события атак — кольцевой буфер для отрисовки (не сохраняется).
- Толпа раздвигается по спискам врагов на тайлах, не больше 6 соседей на врага.
- Удаление — перестановкой последнего.

**Урон** (`GameWorld`):
- `damage_building`: при нуле здание разрушается без возврата, содержимое теряется (сигнал
  `building_destroyed`); `damaged` — id повреждённых для полосок.
- Центральный шлюз не разрушается: мир помечается `breached`, и `Run.step` делает аварийный телепорт
  на случайную соседнюю планету. Площадка переезжает с прочностью зданий и грузом, шлюз пересобирается целым.
- `damage_drone` → `kill_drone`: инвентарь и сырьё очереди (`CraftQueue.drain_into`) — в `DroneCrate`,
  через паузу `respawn_drone` у шлюза с неуязвимостью. Подбор — в тике дрона.
- В творческом режиме угрозы нет и дрон неуязвим.

**Точки появления** (`SpawnPoints`): у краёв карты в разных секторах, с проходом до центра.
Генератор прорубает коридор через скалы; у готовых карт точки только ищутся.

**Отрисовка**:
- `EnemyRenderer` — один MultiMesh с поворотом по направлению, атлас врагов 48 px;
  издалека враги рисуются крупнее.
- `CombatOverlay` — полоски прочности (здания, раненые враги), трассеры и искры атак, обломки, груз.
- `SpawnMarkers` — зоны появления, пульсируют перед волной.
- HUD: `ThreatPanel` (отсчёт, волна, непрерывная атака, враги, прочность шлюза) и уведомления;
  отсчёт появления сбитого дрона; итог аварийного телепорта.

**Сохранение** (версия 2): таблица id врагов; у мира — точки появления, груз, разрушенные, флаг прорыва,
массивы врагов, у планеты — расписание угрозы с очередью появлений и RNG, поле потоков вместе с незаконченным
пересчётом; прочность повреждённых зданий. Бой после загрузки идёт так же, как без неё (тест).

## Оборона (этап 10)

**Данные**:
- `TurretDef` (наследник `BuildingDef`): дальность и мёртвая зона, перезарядка, поворот ствола, конус выстрела,
  разброс, запас выстрелов, `artillery`, виды патронов `TurretAmmo` — предмет, выстрелов из предмета, урон,
  радиус взрыва, скорость снаряда, множитель перезарядки.
- Раздел меню `DEFENSE`: на этапе 10 — медная и титановая стены, пулемёт и артиллерия; с этапа Д —
  каменная стена 1×1 (линией) и пулемётная турель на патронах «гильза + наполнитель». Артиллерия
  осталась в коде (тесты строят её описание в коде). Стены и турели не поворачиваются.
- `DroneDef`: урон, перезарядка, дальность и скорость пули автопушки; прочность в секунду для ремонта.

**Турель** (`Turret`):
- Запас — стопка видов патронов, последний пришедший стреляет первым. Патроны принимаются
  от любых соседей (`accept_item`) и руками (`player_put`); окно турели показывает запас.
- Без патронов турель спит до прихода предмета. Без врагов на планете проверяет раз в 15 тиков,
  без цели в радиусе ищет раз в 10.
- С целью бодрствует: упреждение по скорости врага (позиция − прошлая позиция) × время полёта, поворот ствола,
  выстрел в пределах конуса. Разброс — от RNG мира. После выстрела будит ленты, ждавшие места.
- Цель хранится как индекс и uid врага: после перестановки индексов (гибель других) цель ищется заново.

**Снаряды** (`ProjectileSystem`, мир):
- Пуля: за тик проверяется отрезок пути против тел врагов (без пролёта сквозь), урон первому.
- Снаряд артиллерии: летит в точку прицела и взрывается, урон всем в радиусе.
- Урон — `EnemySystem.hurt`: погибшие остаются с прочностью ≤ 0 до `remove_dead` в конце шага снарядов,
  чтобы индексы не сбивались посреди прохода.
- Поиск врагов (`find_nearest`, `query_circle`) идёт по спискам врагов на тайлах; если врагов меньше площади
  поиска, перебираются все.

**Порядок тика**: здания (турели стреляют) → угроза → поле потоков → враги → снаряды и уборка погибших → дрон
(автопушка, ремонт).

**Дрон**: автопушка стреляет по ближайшему врагу в радиусе; ремонт — ближайшая повреждённая постройка в радиусе
строительства, бесплатно, `repair_per_second` в секунду.

**Интерфейс**:
- `TurretView` — стволы, отдача и вспышка выстрела; радиусы всех турелей по T.
- Радиус турели в руке, под курсором и выбранной — в `PlacementPreview`.
- `CombatOverlay` — пули, снаряды по дуге, взрывы, гибель врагов; `DroneView` — луч ремонта и выстрел пушки.
- `AttackIndicator` — уведомление «Враги атакуют постройки» (не чаще раза в 20 с) и стрелка у края экрана к месту атаки.
- Панель угрозы считает уничтоженных врагов, итог телепорта — тоже.

**Сохранение**: снаряды в полёте, запас и прицел турелей (`save_state`), пушка и цель ремонта дрона.

## Контент ранней игры, энергия, жидкости, исследования (этап Д)

Весь прежний контент (медь, свинец, титан, графит, кремний, дробилка, сепаратор, клапаны, титановые версии,
хранилище, артиллерия) удалён из данных. Новый контент — столбцы Early game и Early midgame из заметок
пользователя; таблицы и числа — `docs/CONTENT.md`. Данные генерирует скрипт по таблицам, код систем
(артиллерия, уровни логистики `throughput_of`, `ProduceWeighted`) остался для следующих этапов.

**Маршрутизатор с приоритетами** (вместо клапанов). Настройка — `{"in": сторона, "out": сторона}` или `null`,
стороны относительно поворота (R и вставка с поворотом поворачивают их вместе со зданием):
- приоритетный выход: предмет сначала предлагается этой стороне, по кругу — только если она не приняла;
- приоритетный вход: пока на ленте с этой стороны есть предметы, едущие в маршрутизатор
  (`ConveyorSystem.has_items_heading_to`), остальные входы получают отказ.
Панель настройки — две строки кнопок «✕ → ↓ ← ↑», метки приоритетных сторон рисуются на здании.

**Заводы** (`Crafter`, `CrafterDef.recipes` + `recipe_mode`):
- `FIXED` — один рецепт; `AUTO` (печь) — рецепт выбирается по первому пришедшему сырью, сменить можно,
  когда цикл закончен и вход пуст; `SELECT` (сборщик) — рецепт — настройка здания (id), при смене сырьё
  начатого цикла возвращается во вход. Закрытые исследованием рецепты выбрать нельзя.
- Цикл — прогресс: за тик `+ скорость / тиков_на_цикл`, скорость = удовлетворённость сети (электрические)
  или 0 без топлива (печь: `fuel_use` кВт, запас `fuel_capacity`). Пока цикл идёт, завод бодрствует
  и выставляет `power_request`; без топлива спит до прихода угля.
- Статусы: работает, нет сырья, выход забит, нет питания, нет топлива, нет рецепта.
- Бур так же: прогресс × удовлетворённость, бодрствует, пока буфер не полон.

**Электросеть** (`power/PowerGraph`, у каждого `GameWorld`):
- `PowerPole` хранит провода смещениями до других опор (`link_offsets`); это его настройка для пипетки,
  переезда площадки и сохранения, но в панели настройки её нет. Провод действует, пока опора на том конце
  существует и в радиусе. Опора, поставленная игроком (`GameWorld.build`), соединяется с ближайшими
  (`auto_link`, до `max_links`); при загрузке и переезде провода берутся из настройки. Снос опоры убирает
  провода к ней у соседей.
- Сети — компоненты связности опор (union-find по id); потребители (`def.power_use > 0`) и генераторы
  (`is_power_generator`) в зоне опор (`supply_size`×`supply_size`) принадлежат сети опоры с меньшим id.
  Состав пересчитывается лениво при изменении построек и проводов (`mark_dirty`) и в сохранение не пишется.
- Тик (в начале шага мира): спрос = Σ `power_request`·dt; мощность = Σ `get_power_capacity_kj(dt)`;
  `satisfaction = min(1, мощность / спрос)`; генераторы получают `draw_power_kj(свой_предел × нагрузка)`.
  Потребители читают `get_power_satisfaction()` в своём `update_tick`.
- `Generator`: `FUEL` (термогенератор — уголь, КПД) или `STEAM` (пар из порта: `steam_energy` кДж на единицу).
- Интерфейс: `NetworkView` — провода, зоны опор (пока в руке электрическая постройка или курсор над опорой),
  значки у потребителей: красный — вне зоны опор, жёлтый — энергии не хватает. Призрак опоры показывает
  зону и радиус провода.

**Жидкости** (`fluids/FluidGraph`, у каждого `GameWorld`):
- Узлы — трубы (`Pipe`) и порты построек (`Building.get_fluid_ports()` → `Port(сторона, жидкость, группа)`);
  порт — вся сторона здания. Соседние трубы и труба с портом на смежной стороне соединены; порты разных
  построек, стоящих вплотную, — тоже (генераторы пара можно ставить цепочкой). Порты одной группы
  внутри здания связаны (пар проходит сквозь генератор).
- Сеть — union-find: одна жидкость, общий запас, ёмкость = трубы + `PORT_CAPACITY` на порт. При пересборке
  запас старых сетей делится по узлам и собирается в новые — разрез трубы делит жидкость.
- `Pump` — на тайлах воды, `pump_per_tile` × тайлы в секунду в соседние сети, без электричества.
  `Boiler` — вода с одной стороны, пар с противоположной, уголь → пар (`fuel_power`, `steam_per_second`).
- Сохранение: запас каждой сети по ключу минимального узла; сеть пересобирается до записи.

**Исследования** (`research/`, общие для забега — `Run.research`, ссылка у обоих миров):
- `ResearchDef`: стоимость (набор × количество), предшествующие, открываемые постройки и рецепты.
  `Registry.get_building_research/get_recipe_research` — что закрывает постройку или рецепт.
- `ResearchState`: завершённые, прогресс, выбранное; ручная очередь — наборы первого уровня из инвентаря,
  `MANUAL_SECONDS` на набор в тике забега; `ScienceWorkshop` отдаёт наборы в выбранное исследование
  (`add_kit`) с прогрессом от электричества и засыпает, когда выбранному исследованию наборы не нужны
  (смена выбора будит цеха).
- Закрытые постройки нельзя скрафтить (`CraftQueue.recipe_filter`), в меню они затемнены с подсказкой;
  рецепты сборщика — недоступны. В творческом режиме открыто всё.
- Интерфейс: `ResearchWindow` (J или кнопка в HUD) — карточки, выбор кликом, «Сдать наборы», очередь;
  уведомление о завершении.

**Эффекты патронов** (`TurretAmmo`): осколки (`splash_radius` у пули — взрыв в точке попадания),
поджог (`burn_dps`, `burn_seconds` → `EnemySystem.ignite`, урон в тике врагов, не суммируется — берётся
сильнее/дольше), скорострельность (`reload_multiplier`). Горящие враги подсвечиваются в `CombatOverlay`.

**Порядок тика мира**: жидкости → электросеть → здания → угроза → поле потоков → враги → снаряды → дрон.

**Сохранение** (версия 3): таблица id жидкостей, у мира — запасы сетей труб, у забега — исследования.
Тест точного продолжения строит фабрику с термо- и паровой станцией, трубами и ручной очередью исследований.

## Правки после этапа Д

По списку игрока из Obsidian (`WarpFactor/Добавить.md`).

- **Дерево исследований** (`ResearchTreeView`): столбец — глубина (самая длинная цепочка предшественников),
  ряд — не выше ряда первого предшественника; линии-ломаные от предшественника к следующему, цвет по состоянию.
  Зависимости: Добыча → Логистика → Промышленность → Автоматизация науки, Добыча → Оборона.
- **Провода** рисуются прямыми отрезками.
- **Протягивание ленты** (`LinePlanner.plan_belt`): по трассе классифицируются тайлы — лента, препятствие
  (постройка, скала, вода; на концах и углах чужая постройка тоже препятствие), поперечная лента, перекрёсток.
  Сплошной участок препятствий на прямом отрезке перекрывается парой мостов (вход перед ним, выход за ним,
  в пределах `link_range`; соседние пары сцепляются в цепочку), поперечная лента заменяется перекрёстком.
  Мосты и перекрёстки считаются по инвентарю заранее; не хватает — препятствие остаётся красным призраком,
  поперечная лента не трогается. Мост-призрак несёт свою настройку (смещение до выхода), и `_build_ghosts`
  применяет её вместо настройки из пипетки.
- **Вода**: `BuildingDef.allowed_on_fluid`; `BuildingManager.check_place` возвращает `ON_FLUID` для построек
  без флага на тайлах месторождения жидкости (флаг у трубы, подземной трубы и насоса).
- **Окна зданий** (`WindowSection`, `Building.get_window_sections`): ряды ячеек (сырьё рецепта с бледными
  подсказками, топливо, продукт, добыча, патроны) и полоски (прогресс, питание, горение, мощность, вода, пар,
  подача насоса, жидкость в трубах, нагрузка сети). `InventoryWindow` перестраивает элементы только при смене
  набора разделов (подпись: виды, заголовки, число ячеек), иначе обновляет значения. Клик по ячейке —
  `player_take`, клик по инвентарю — `player_put` (здание само раскладывает топливо и сырьё).
- **Бур** отдаёт добычу только соседям с лицевой стороны (`rotation`), стрелка на здании и на призраке;
  разгрузчик забирает из бура с любой стороны.
- **Подземная труба** (`UndergroundPipe extends Pipe`): поворот — направление подземного участка, сверху
  открыта только противоположная сторона (`Pipe.connects_side`). Пара — ближайшая по направлению подземная
  труба, смотрящая навстречу, в пределах `underground_range`; соединение только взаимное. `FluidGraph`
  учитывает открытые стороны у стыков труб и портов и объединяет пары. При установке
  `BuildingDef.placement_rotation` разворачивает выход к свободному входу — вход и выход ставятся одним поворотом.
  С постройкой для жидкостей в руке `NetworkView` показывает подземные участки пунктиром, непарные — красной меткой.
- **Карта** ×3 по стороне: обычная 336–480 × 252–360, пустошь 240–336 × 180–252; шумы пола и скал реже
  (крупные пятна и скальные массивы), залежей меньше (`deposits_per_10k` 0.6), радиус залежи 6–10 тайлов.
  Враги по-прежнему появляются у краёв.
  Генерация 345×324 — ≈350 мс.
- **Камера** не показывает пространство за краем карты: центр взгляда ограничен половиной видимой области,
  а если карта меньше экрана по оси — стоит в её центре (`CameraController.clamp_axis`).
- **Опоры** протягиваются с шагом `floor(wire_range)` (7 тайлов) — `PowerPoleDef.get_line_step`.

## Энергия, этажи базы и шлюз по исследованиям (этап 11)

**Модель базы.** Мобильная база — два этажа: площадка шлюза на планете (`GameWorld.pad_rect`, переезжает при
телепорте) и подземный этаж — отдельный мир `Run.base` (раньше «база»). Размеры задают исследования:
`RunDef.pad_start_size/pad_size_step` и `BaseDef.start_size/size_step`. Карта этажа сразу наибольшего размера
(`BaseDef.size`), за открытой частью — пол `void` (не строится); `GameWorld.play_rect` — открытая часть,
дрон (`Drone`) и камера (`CameraController`, границы — прямоугольник) за неё не выходят.

**Эффекты исследований** (`ResearchDef.effects`, `ResearchState.count_effect/has_effect/max_effect`, кэш
по числу завершённых): `underground`, `underground_size`, `pad_size`, `gateway_items`, `gateway_ports`,
`gateway_power`, `gateway_fluids`. `Run.apply_research_effects()` (на завершение исследования и при создании
забега) растит площадку (`GameWorld.resize_pad`: свободные тайлы новой части — платформа без руды) и открытую
часть этажа (`open_area`), помечает сети для пересборки и будит шлюзы. После загрузки вызывается
с `notify = false` — размеры сверяются, состояние симуляции не трогается. Мир шлёт `terrain_changed`
(террейн обновляет прямоугольник одной загрузкой обзорной текстуры) и `bounds_changed` (рамка площадки, камера).
Генератор планет расчищает землю под наибольшую площадку (`generate(node, pad_size, clear_size)`).

**Шлюз.** Проход на этаж закрыт без `underground` (`Run.is_over_gateway` — подсказка, `can_use_gateway` — переход).
Предметы — только с `gateway_items`. Порты — тайлы сторон по порядку «середина, края» (`GatewayDef.get_port_tiles`),
открыто `1 + gateway_ports`; у каждого выходного порта свой таймер пропускной способности, очередь вмещает
`capacity × портов`. Стрелки рисуются у каждого открытого порта.

**Лифт** (`Lift`, `LiftDef`). Пара — в том же месте относительно шлюза на другом этаже (`Run.pair_origin`).
`GameWorld.lift_check` (задаёт забег) проверяет место: этаж открыт и лифт изучен, лифт на площадке или в открытой
части этажа, пара помещается туда же на свободное место (`Check.LIFT_AREA/LIFT_PAIR/LOCKED`). Забег слушает
`building_added/removed` обоих миров: новый лифт находит или ставит пару, снос сносит пару. Направление — общая
настройка (`ConfigKind.MODE`, при смене буфер переезжает в лифт исходного этажа); буфер хранится в лифте
исходного этажа, лифт другого этажа раздаёт соседям с пропускной способностью ленты. При телепорте поиск пар
выключен, пока новая планета не станет текущей; потом лифты площадки связываются заново, осиротевшие на этаже
сносятся. После загрузки — `Run.relink_lifts()`.

**Электросеть** (`PowerGraph`). `prepare()` пересобирает сети при изменениях и собирает на тик спрос, возможную
выработку и пределы аккумуляторов; `balance(group)` — общий баланс группы сетей: сначала генераторы на спрос,
нехватку — разрядом аккумуляторов, излишек — зарядом; генераторы тратят пропорционально взятому. В забеге миры
`managed`: `Run.step` готовит обе сети, объединяет сети, связанные шлюзом и лифтами (`is_power_link`, если открыто
`gateway_power`; здание-связь в зоне опоры принадлежит её сети), и балансирует группы; `update()` мира пуст.
Отдельный мир (тесты) балансирует каждую сеть сам. `Accumulator` — `is_power_storage`, запас в `save_state`.
История сети (`PowerHistory`, по ключу — наименьший id опоры, переживает пересборку, не сохраняется): средние
спрос, выработка и доля заряда за 30 тиков, 120 точек.

**Жидкости между этажами.** Шлюз с `gateway_fluids` получает порты на двух свободных сторонах (две группы),
лифт — порты со всех сторон. `Run.step` до тиков миров выравнивает долю заполнения связанных сетей одной
жидкости (не больше `FLUID_LINK_RATE` за тик).

**Порядок шага забега**: жидкости между этажами → электросети этажей → тик планеты → тик этажа → исследования → телепорт.

**Интерфейс.**
- Окно опоры: нагрузка, заряд аккумуляторов, график (`WindowSection.Kind.GRAPH` → `PowerChart`) и состав сети
  (`Kind.TEXT`). Окна аккумулятора и лифта — полоски и очередь.
- Оверлей электросетей (P, `NetworkView.power_overlay`): зоны опор цветом сети, подпись «спрос / выработка»,
  перегруженные сети мигают красным, связанные с другим этажом — «⇅».
- Дерево исследований раскладывает 23 узла по столбцам глубины (прокрутка).
- Подсказка над шлюзом: закрытый этаж — название нужного исследования.

## Развитие: дерево, угольный бур, ветка дрона (этап 12)

**Дерево исследований.** Корень — «Электрика» (термогенератор и опора ЛЭП), от неё три направления:
«Трубы и насосы» → «Паровая энергия» → «Аккумуляторы»; «Электробур» → «Промышленность» →
«Автоматизация науки» и «Электробур» → «Логистика»; «Оборона». Этажи базы, шлюз и лифты висят
на «Электробуре» (бывшая «Добыча», тот же id `mining`). Отдельный корень — ветка дрона:
«Скорость дрона I», от неё четыре цепочки по три ступени. Всего 41 исследование.

**Угольный бур** (`coal_drill`, тот же `Drill`/`DrillDef`). Один тайл, `fuel_use` вместо `power_use`:
топливо лежит в `fuel_counts`, горящий остаток — в `fuel_energy` (как у `Crafter`), и то и другое
в `save_state`. Принимает топливо с любой стороны (`accept_item`), а если добывает топливную руду,
`_wants_fuel` уводит добытое в собственный бак, пока тот не полон, и только потом на выход. Один тайл
против четырёх у электробура даёт ровно четырёхкратную разницу в скорости; `tier = 1` — малахит
только электробуром. Доступен без исследования: это стартовая автоматизация до «Электрики».

**Улучшения дрона.** `DroneDef` хранит шаг каждой ступени (`speed_step`, `mine_speed_step`,
`health_step`, `gun_damage_step`, `repair_step`), `Drone` — число ступеней и считает характеристики
(`get_speed`, `get_mine_ticks`, `get_max_health`, `get_gun_damage`, `get_repair_per_second`).
`Run.apply_research_effects` вызывает `Drone.apply_upgrades(research, notify)`: при завершении
исследования прочности дрон лечится на прирост, при загрузке (`notify = false`) — нет, иначе
разойдётся сохранение. Сами ступени не сохраняются: они выводятся из исследований.

**Очередь исследований.** `ResearchState.queue` — до `QUEUE_MAX` (5) id. Завершение текущего
берёт из очереди первое доступное (`_take_from_queue`, сигнал `next_taken`); недоступные ждут
своих предшественников, завершённые выбрасываются. Очередь сохраняется. В окне J: ЛКМ по карточке —
выбрать, ПКМ — поставить в очередь или убрать; номер места виден в карточке, состав — внизу окна.

**Данные** генерируются скриптами `tools/data/` (лежат в репозитории, пути относительные):
`make_content.py` — предметы, руды, рецепты, постройки, исследования; `make_csv.py` — `i18n/strings.csv`;
`make_content_doc.py` — `docs/CONTENT.md`; `make_enemies.py` — враги. Запуск: `python tools/data/make_content.py`.

## Удобство, творческий режим и чётный шлюз (этап 13)

**Шлюз чётного размера.** `GatewayDef` хранит два размера: `start_size` (2) и `grown_size` (4);
`BuildingDef.size` — наибольший из них. Занимаемый размер живёт у здания (`Building.size`,
`get_size()`, `get_rect()`), выставляется при установке (`get_initial_size()`) и меняется
`BuildingManager.resize_building(b, size)`: тот чистит старые тайлы, шлёт `building_removed`,
сносит попавшее в новый прямоугольник, переносит здание и шлёт `building_added` — соседство, сети
и отрисовка обновляются сами. `Run._grow_gateways()` вызывается из `apply_research_effects` и растит
оба шлюза, когда открыты все «Порты шлюза». Центр шлюза (`origin + size / 2`) — точка симметрии:
площадка теперь ровно окружает его. Размер пишется в сохранение (`VERSION 4`), потому что постройки
загружаются раньше исследований.

**Трубы протягиванием.** `LinePlanner.plan_pipe` — как `plan_belt`, но сплошной участок препятствий
перекрывается парой подземных труб (вход перед участком, выход сразу за ним, если хватает дальности
и самих труб); стоящие трубы остаются. `LinePlanner.plan_underground` ставит ряд подземных труб
парами на наибольшем расстоянии, следующая пара — вплотную к предыдущей, так что линия идёт под землёй
и тратит минимум труб. Одиночный клик по-прежнему разворачивает выход ко входу (`placement_rotation`).

**Отрисовка труб.** Стыки труб и заполнение сетей уехали из `NetworkView` (перерисовка каждый кадр
обходом всех труб мира) в `PipeLayer` + `PipeChunkView` — по ноде на чанк, как у `BuildingLayer`.
Чанк перерисовывается, только когда сети труб пересобрались (`FluidGraph.version`) или заполнение сети
перешло через ступень (`FILL_STEPS`). На этаже, заставленном трубами, кадр перестал зависеть от их числа
(замер в автопрогоне: 560 труб на экране — 8.3 мс/кадр, как без них).

**Быстрый обмен.** Shift+ЛКМ по зданию забирает накопленную продукцию (`Building.get_player_output_stacks`,
у заводов — только выход, у бура — только добытое), Shift+ПКМ загружает в него всё подходящее из инвентаря
(`GameWorld.player_fill`). Обрабатывается в `ToolController._quick_transfer` до обычных кликов.

**Творческий режим.** `BuildingDef.creative_only` — постройка видна в меню и ставится только в творческом
забеге (`GameWorld.is_def_allowed`, `Check.LOCKED`). Четыре блока на одном скрипте `CreativeBlock`
(`CreativeBlockDef.kind`): источник предметов, энергии, жидкости и поглотитель; настройка — `ConfigKind.SOURCE`
(что выдавать + ступень скорости из `rates`). Волны в творческом режиме включаются в панели угрозы
(`Run.set_creative_threat`, `call_creative_wave`). Дерево исследований получило «Полигон»
(`ResearchDef.creative_only`, бесконечная стоимость) и кнопки «Исследовать заново» (`reset_progress`,
выключает «всё открыто») и «Открыть всё» (`unlock_everything`).

**Мелочи.** График сети получил четвёртый ряд — возможную выработку (`PowerHistory.capacity`), а ряды
включаются кнопками под графиком. Колесо над панелью интерфейса больше не меняет масштаб мира
(`CameraController._wheel_over_ui`). Колесо над деревом исследований приближает его. Над добываемым тайлом
всплывает «Камень ×11» (`Drone.last_mined_*`, рисует `DroneView`). У края экрана — маленькие красные стрелки
к врагам по секторам (`AttackIndicator`). Появился водный бак (большая труба на 4000 единиц).

## Игроки и слой команд — основа сетевой игры (этап 14)

Сетевая модель выбрана детерминированная (lockstep, как в Factorio): по сети ходят только команды
игроков, каждый участник считает одну и ту же симуляцию. Этап 14 — вся подготовка к ней в офлайне;
сам транспорт будет в этапе 15.

**Игроки.** `Player` (`player/player.gd`) — id, имя, цвет и свой `Drone` с инвентарём и очередью
крафта. `Run.players` отсортирован по id, `Run.local_player` — за кого играет этот клиент,
`Run.drone` теперь свойство и возвращает дрона локального игрока. Общие на всех: планета,
подземный этаж, постройки, исследования и ступени улучшений дрона (их даёт исследование, поэтому
они автоматически одинаковы). Игроки могут быть на разных этажах.

**Мир и дроны.** `GameWorld.drones` — дроны, которые сейчас в этом мире, по возрастанию id игрока
(порядок важен: от него зависит порядок в тике). Переезд между мирами — только `Drone.move_to_world`,
чтобы списки не разъезжались. `GameWorld.view_drone` — чей мир показывают, `GameWorld.actor` —
от чьего лица выполняется действие (забег ставит его на время команды); `acting_drone()` выбирает
между ними. Враги целятся в ближайшего доступного дрона (`_nearest_drone`), урон получает он же.

**Команды.** `Command` (`core/command.gd`) — одно действие игрока: вид, id игрока, номер команды
и аргументы (здания — по id, постройки и рецепты — по строковому id, чтобы команду можно было
отправить по сети). `CommandQueue` складывает команды по тикам: команда, отданная в тике T,
применяется в тике T + `delay` (в одиночной игре 0, в сетевой — несколько тиков на дорогу).
Внутри тика команды всегда сортируются по (игрок, номер), поэтому порядок получения по сети
не влияет на результат. `Run.step()` начинается с `_apply_commands()`.

**Интерфейс ничего не меняет сам.** Инструменты и панели вызывают `world.submit(...)` вместо прямых
`build/demolish/configure/player_take/...`. Протягивание ленты — одна команда со списком мест;
связывание мостов и подсказки («нет постройки», «далеко») происходят при выполнении команды,
подсказки — только тому, чья команда. Движение дрона уходит командой лишь при смене направления.
Следствие: действие применяется в ближайшем тике, а не мгновенно (в паузе — после снятия паузы).

**Проверка без сети.** F7 (в творческом режиме) добавляет игрока, F8 переключает между игроками:
можно вдвоём строить, ходить по разным этажам и проверять раздельные инвентари. `DroneView` рисует
всех дронов текущего мира цветом их игрока, чужие подписаны именем.

**Сохранение.** Секция `players` вместо `drone`, `VERSION 5`: у каждого игрока имя, этаж и полное
состояние дрона; в `run` — `local_player` и `next_player`. Команды не сохраняются: они применяются
в тот же тик, в котором отданы.

**Тест детерминизма** (`_test_command_determinism`): два забега получают одинаковый набор команд,
но в разном порядке отправки; после одинакового числа тиков их сохранения совпадают байт в байт.
Это и есть проверка того, что lockstep будет работать.

## Сеть: lockstep поверх слоя команд (этап 15)

**Модель.** По сети ходят только команды игроков. Каждый участник считает одну и ту же симуляцию,
поэтому трафик не зависит от размера фабрики: хоть десять тысяч лент — по сети идут десятки байт.

**Кто за что отвечает.**
- `NetTransport` (`net/net_transport.gd`) — доставка пакетов. Игра знает только этот интерфейс,
  поэтому `EnetTransport` (локальная сеть и прямой IP) позже меняется на Steam P2P без правки логики.
- `NetProtocol` — что именно летает: HELLO, WELCOME (снимок), TICK (окончательный список команд
  на тик), COMMANDS, CHECKSUM, RESYNC, TIME, BYE. Версия протокола сверяется при входе.
- `NetSession` — сам lockstep: планирование тиков, приём и рассылка, вход в игру, контрольные суммы.
- `LanDiscovery` — поиск игр в локальной сети по широковещательному UDP (со Steam его заменит список лобби).

**Ход времени.** Хост планирует тик T заранее, за `INPUT_DELAY` тиков (4 ≈ 130 мс): собирает
накопленные команды всех участников, рассылает пакет TICK и кладёт тот же список себе.
Клиент считает тик, только когда получил его список (`can_step`, `confirmed_tick`), — поэтому все
применяют одни и те же команды в одном и том же тике. Команды клиента не применяются у него сразу:
они идут хосту и возвращаются в составе TICK. Порядок внутри тика — по (игрок, номер команды).

**Вход в игру.** Хост сериализует забег (то же сохранение, сжатое ZSTD), шлёт снимок и все уже
запланированные тики после него; игрок добавляется командой PLAYER_ADD с готовым id, поэтому
у всех участников он появляется одинаково. Клиент загружает снимок, ставит свой тик и играет дальше.

**Расхождение.** Каждые `CHECKSUM_EVERY` тиков считается отпечаток состояния (`Run.state_hash`:
тик, постройки, предметы на лентах, дроны и инвентари, исследования — без сериализации, быстро).
Клиент шлёт его хосту; если не сошлось — хост шлёт свежий снимок, клиент продолжает с него
и все видят сообщение.

**Выход и возвращение.** Дрон вышедшего остаётся стоять со всеми вещами (хост командой обнуляет
его движение и добычу). Вернувшийся под тем же именем занимает своё тело.

**Пауза и скорость** — общие, но идут мимо тиков отдельным пакетом TIME: на паузе тики не считаются,
и команда в очереди просто никогда бы не применилась.

**Где это включается.** Главное меню → «Подключиться» (список игр в локальной сети и прямой адрес);
меню паузы → «Открыть для сети». Сессия живёт в автозагрузке `Session`, поэтому переживает
переход между сценами: клиент получает мир ещё в меню и уже с ним входит в игровую сцену.

**Проверки.** `_test_net_*` в логических тестах гоняют протокол на транспорте в памяти
(`tests/support/loopback_transport.gd`): вход, совместная игра, расхождение и починка, выход
и возвращение. `tests/net_check.tscn` — то же самое, но через настоящий ENet на 127.0.0.1,
со сверкой отпечатков состояния по одинаковым тикам.
